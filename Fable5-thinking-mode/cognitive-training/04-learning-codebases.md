# 04 · 专题：学习复杂程序包

> 适用对象：micrOMEGAs 这类几十万行的物理软件包、任何陌生的大型框架。
> 核心立场：**理解是构建出来的，不是读出来的**——阅读只是构建过程中的
> 取材动作。

## 1. 先质疑"学会"（五步法第 1 步）

"完整理解这个包"几乎永远是蠢需求。先写一行**目的驱动的定义**：

| 你的真实目的 | "学会"的定义 | 大致要读的量 |
|-------------|-------------|:---:|
| 调用它算物理量 | 会写一个 project、读懂输入输出约定 | ~2% |
| 改它的某个物理模块 | 上一行 + 该模块的数据流和邻接接口 | ~10% |
| 给它做二次开发框架 | 上一行 + 构建系统、核心数据结构、扩展点 | ~25% |
| 全部读完 | ——没有目的对应这一行 | 永远不 |

你对 micrOMEGAs 的路线就是活例子：从"会用"（JSON I/O 的 project 模板）
到"改模块"（directDet.c 加 DeltaDD、improveCS.c 加 R(s) 修正），每一步
只补当步需要的理解，从来没有"通读"。**这个模式是对的，把它变成自觉。**

## 2. 第一天协议：跑起来 > 读明白

理解一个系统最快的路径是让它**在你手里动起来**——能动的系统才有反馈环。
第一天只追三个命令（trifecta）：

```text
1. 构建命令   （它怎么从源码变成可执行？）
2. 运行命令   （最小的"hello world"级调用长什么样？）
3. 测试命令   （它自己怎么验证自己？）
```

三个命令到手且跑通，第一天就是成功的——**哪怕一行源码都没读**。因为
从此你有了实验台：任何关于它的猜想都可以两分钟内问现实，不用问文档。

## 3. 20 分钟侦察卡（固定问题清单）

计时 20 分钟，只回答这九个问题，到点收笔：

```markdown
## 侦察卡：<包名>                                日期：

1. 入口在哪？（main / CLI / 顶层 API）
2. 构建/运行/测试三命令是什么？
3. 目录结构透露的架构是什么？（一句话）
4. 核心数据结构是哪 1–3 个？（"给我看数据表"——数据结构比算法诚实）
5. 一次典型调用的数据流：输入从哪进 → 经过哪几站 → 输出从哪出？
6. 配置从哪来？（文件/环境变量/编译期开关）
7. 命名惯例是什么？（前缀、大小写——之后搜代码全靠它）
8. 【不读清单】哪些目录明确不读？（vendored、生成物、废弃路径）
9. 最让我意外的一点是？（意外 = 你的先验错了 = 最值得记的信息）
```

第 8 题是五步法第 2 步（删除）应用于阅读范围；第 9 题是校准练习——
每张侦察卡都在给你的直觉打分。

## 4. 纵切法：跟一条流程走到底

侦察之后不要横向铺开读，选**一条代表性流程**从入口跟到出口。以
micrOMEGAs 为例，就是一条线：

```text
main.cpp 读入 JSON → 模型参数装载 → sortOddParticles()（注意 nextOdd
0-indexed）→ 相关物理量计算（如 relic density 主循环）→ JSON 输出落盘
```

纵切的纪律：

- **跟数据，不跟控制流**。问"这个数组/结构体在每一站被谁改了什么"，
  比追每一个 if 分支高效得多。
- 沿途在自己的笔记里给每一站写**一句话职责**。写不出来的那站，就是要
  停下来细读的地方——其余的站一句话就够，别恋战。
- 一条纵切走完，你脑中就有了这个包的"骨架模型"；之后所有阅读都是往
  骨架上挂肉，有处可挂的知识才留得住。

## 5. 三个高杠杆信息源（多数人不用）

1. **测试即文档**。测试是唯一保证不过时的文档：它展示每个 API 的合法
   调用方式、边界值、以及作者认为值得防御的错误。读 `tests/` 常常比读
   手册快。
2. **git 考古**。`git log --follow <file>` 看一个文件的演化；`git blame`
   看一段怪代码的出生提交——提交信息里往往写着它为什么长这样。对
   "这段代码为什么这么怪"的问题，考古比猜测便宜十倍。
3. **构建系统**。Makefile / CMakeLists 是包的"官方地图"：哪些源文件真的
   参与构建（没参与的直接进不读清单）、有哪些编译期开关（每个开关都是
   一个功能维度）。

## 6. 输出驱动：写你希望入门时就存在的那份文档

学习的收尾动作（也是检验）：给想象中的下一个新人写一页
"我希望第一天就有人给我的说明"。写的过程会精确暴露你理解的空洞——
**空洞在阅读时会绕着走，在写作时绕不过去**（费曼技巧的本质）。

你已经用最大号做过一次了：148 页的 Jarvis-HEP 手册。这里说的是它的
日常微缩版——每学一个包，留一页。顺带的复利:这一页正是喂给任何
AI 助手的最佳上下文，一次写作，人机两用。

## 7. 三天上手计划模板

```markdown
## 三天上手：<包名>

**目的驱动的"学会"定义**（§1 的表里选一行）：

### Day 1 · 让它动起来
- [ ] trifecta 三命令跑通（构建/运行/测试）
- [ ] 20 分钟侦察卡填完
- [ ] 跑通一个最小示例，改一个输入参数，预测输出变化，验证

### Day 2 · 纵切一条流程
- [ ] 选定代表性流程：__________
- [ ] 每站一句话职责，写进笔记
- [ ] 卡壳的那一站细读 + 一次小实验确认理解

### Day 3 · 按目的补深 + 输出
- [ ] 只深入与目的相关的模块（对照不读清单，别越界）
- [ ] 写"给下一个新人的一页"
- [ ] 提取 2–3 条 general rule 进个人规则库
```

三天后你不是"学完了"，而是**具备了随用随学的骨架**——后续每个具体任务
（改一个模块、加一个功能）自带最好的学习路线，见
[03-complex-code-tasks.md](03-complex-code-tasks.md)。
