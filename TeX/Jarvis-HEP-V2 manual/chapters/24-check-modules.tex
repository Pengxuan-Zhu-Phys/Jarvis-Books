\chapter{The check\_modules Smoke Path}
\label{ch:check-modules}

\newthought{Test the workflow before you buy the scan.} \code{check\_modules} is not a
sampler: it is a task \emph{mode} that runs your full calculator/opera/likelihood chain
on a handful of points --- fixed from a \textsc{csv}, or drawn fresh from your real
\yamlkey{Sampling.Method} when no \textsc{csv} is configured --- with the per-sample
command output mirrored to your terminal, so you can validate a card in minutes instead
of discovering a broken \yamlkey{entry} path an hour into a real scan.

\section{Invocation}
\label{sec:check-invocation}

\begin{terminal}
\begin{jcmd}
Jarvis2 check task.yaml
\end{jcmd}
\end{terminal}

\begin{yamlwin}
Sampling:
  mode: check_modules              # or "check-modules"; replaces Method resolution
  # data: "&J/data/check_points.csv"   # optional; see resolution order below
\end{yamlwin}

\yamlkey{data} is \opt. A card with no \yamlkey{Sampling} block beyond \yamlkey{mode} and
a \yamlkey{Method} still runs --- it draws points from that \yamlkey{Method} instead of
reading a file.

\section{Where the points come from}
\label{sec:check-points-source}

\begin{enumerate}
  \item \textbf{A \textsc{csv} path, resolved in order:}
        \yamlkey{Sampling.data} (alias \yamlkey{points\_csv}) in the task card, then
        \yamlkey{EnvReqs.V2.check\_modules.data} in a shared defaults file, then the
        built-in default \file{\&J/data/check\_modules\_points.csv}. The first of
        these that names a file that actually exists wins.
  \item \textbf{If none of those files exist}, \Jtwo\ falls back to drawing
        \yamlkey{EnvReqs.V2.check\_modules.n\_samples} points (default \code{10}) from
        your real \yamlkey{Sampling.Method} --- the same sampler your production scan
        would use, including \sampler{Dynesty} and \sampler{MultiNest}.
\end{enumerate}

\begin{yamlwin}
EnvReqs:
  V2:
    check_modules:
      data: "&J/data/check_points.csv"   # optional override
      n_samples: 10                        # sampler-fallback point count
\end{yamlwin}

Both routes end up at the same place: a small batch of \code{Sample}s runs through the
identical execution plan a real scan uses, and the console shows everything.

\begin{jnote}
\textbf{A \textsc{csv}'s columns are \emph{u-space} coordinates, one per declared
variable, in the order of \yamlkey{Sampling.Variables}} --- not physical parameter
values. This is the same unit-cube language every sampler proposes in
(Section~\ref{sec:uspace}); the Worker maps it to physical values exactly as it would
for any other Sample. If your card declares no \yamlkey{Variables} (a check-only card
with no real sampler behind it), column names fall back to the \textsc{csv}'s own
header row, and finally to a bare \code{x,y} for the oldest cards.
\end{jnote}

\begin{jwarn}
When \yamlkey{Sampling.Method} is present, it is validated in full --- exactly like a
real scan (\yamlkey{Bounds}, \yamlkey{Variables}, everything in
Chapters~\ref{ch:multinest}--\ref{ch:dynesty} included) --- \emph{even if} a
\textsc{csv} is also configured and would otherwise satisfy the run. An invalid
\yamlkey{Method} only survives unnoticed when \emph{no} \yamlkey{Method} is set at
all and a \textsc{csv} resolves instead. If you keep a leftover \yamlkey{Method} from
copy-pasting a real scan card, either delete it or keep it valid
(Section~\ref{sec:nested-validation}).
\end{jwarn}

Everything else in the card --- \yamlkey{Calculators}, \yamlkey{Operas},
\yamlkey{Likelihood}, \yamlkey{LibDeps} --- is exercised exactly as in a real scan:
same Workers, same execution plan, same archive path.

\section{What you see}
\label{sec:check-output}

For each point, the console shows what a production scan writes only to the Sample's
private log: the calculator banner, the resolved command line, the raw
stdout/stderr of every external command, and the captured observables --- ending in the
usual archive and a normal \file{DATABASE/} record. The mirroring uses the same
rendered text as the file log, so what you debug is what production records.

\section{The habit}
\label{sec:check-habit}

\begin{enumerate}
  \item Keep \file{data/check\_points.csv} in the project: two or three points whose
        expected observables you know --- a published benchmark, a point you computed
        by hand, given as u-space coordinates for your declared \yamlkey{Variables}.
  \item Run \cli{Jarvis2 check} after \emph{any} edit to \yamlkey{execution} blocks,
        \yamlkey{Dump} variables, or \yamlkey{entry} paths.
  \item Compare the captured observables against the known values before launching the
        scan.
\end{enumerate}

\begin{jtip}
The check points double as an integration test for tool upgrades: after rebuilding an
external calculator, one \cli{Jarvis2 check} against known-good numbers tells you
whether physics changed before any scan does.
\end{jtip}

\begin{jtip}
No fixed points yet and just want a fast smoke of a \sampler{Dynesty} or
\sampler{MultiNest} card? Skip the \textsc{csv} entirely --- \cli{Jarvis2 check} draws
\code{n\_samples} real points from your \yamlkey{Bounds}/\yamlkey{Variables} and runs
them through the full pipeline, no separate fixture to maintain.
\end{jtip}
