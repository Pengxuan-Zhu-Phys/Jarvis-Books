\chapter{The Task Card}
\label{ch:task-yaml}

\newthought{Six keys. That is the entire top-level vocabulary of a task card}, and
everything in Part~\ref{part:task-card} is a detail of one of them. This chapter stays at
that level: it shows the shape of a card, explains why the format is strict in some places
and deliberately not in others, documents the one block small enough to finish here
(\yamlkey{Scan}), and --- most usefully --- teaches you to read the report \Jtwo\ prints
when a card is wrong, because that report names the exact key and usually shows you the
corrected \textsc{yaml}. Each of the other five blocks gets its own chapter, with its own
complete key table. Read this one first and you will know which of them to open, and when.

\section{The shape of a card}
\label{sec:card-shape}

A task card is one \textsc{yaml} document whose top level is a mapping. Exactly six keys
are allowed there, all of them optional as far as the format is concerned:

\begin{terminal}[the whole top-level vocabulary]
\begin{jout}
Scan:         name the scan and say where its outputs go
Sampling:     which method, which variables, which likelihood
EnvReqs:      environment checks and the V2 runtime block
LibDeps:      external tool paths and registered executables
Calculators:  external programs to run per point
Operas:       in-process operators to call per point
\end{jout}
\end{terminal}

A misspelling is not a silent no-op. \code{Calculater} is an error, reported before the
scan can start, with the six legal names printed next to it. The leanest card that does
useful work needs only two of the six --- a \yamlkey{Sampling} block and something to
evaluate, exactly as in the quick start:

\begin{yamlwin}
Scan:
  name: quickstart
Sampling:
  Method: Random
  Bounds:
    "Point number": 20
  Variables:
    - name: x
      distribution: {type: Flat, parameters: {min: 0.0, max: 1.0}}
  LogLikelihood:
    - {name: LogL_Z, expression: z}
Operas:
  Modules:
    - name: TrivialEggbox
      operator: jarvishep2.testing.eggbox.eggbox2d_numpy
      input:  [{name: x, expression: x}, {name: y, expression: y}]
      output: [{name: z, entry: z}]
\end{yamlwin}

Everything else in Part~\ref{part:task-card} adds to that skeleton without changing its
shape. If a card ever looks intimidating, find the six top-level keys first: the rest is
always a subtree of one of them.

\section{Strict where it knows, honest where it does not}
\label{sec:zones}

The natural worry about a format this large is that you will be punished for a typo
somewhere deep in it. So it is worth answering the question directly: \textbf{if you
misspell a key, will you be told?} Usually yes, immediately --- and where the answer is
no, the card can tell you that in advance. One rule covers both cases:

\begin{quote}
\Jtwo\ checks the keys it \emph{acts on}, and does not second-guess the keys it merely
\emph{passes to somebody else}.
\end{quote}

Two nearly identical mistakes show what that buys you.

\paragraph{A key \Jtwo\ owns.} \yamlkey{Sampling} is its own, and so is the settings
block of every sampler \Jtwo\ implements itself. Write \yamlkey{Bounds.Radus} on a
\sampler{Bridson} card and validation stops you immediately with the correct spelling in
hand. You never get to find out at minute forty of a scan that your \yamlkey{Radius} was
never read.

\paragraph{A key that belongs to another program.} On a \sampler{Dynesty} card, the same
\yamlkey{Bounds} block is largely \code{dynesty}'s vocabulary rather than \Jtwo's.
Pretending to know it would mean a new \code{dynesty} release could make a perfectly good
card fail against an allow-list nobody remembered to update. So there \Jtwo\ checks the
keys it acts on and hands the rest through unread. The cost is real and it is stated: a
typo among those is between you and \code{dynesty} (Chapter~\ref{ch:multinest} shows what
that looks like).

That is the whole of it: strict about its own surface, deliberately quiet about somebody
else's, and never silently in between. You are not left guessing which one you are in ---
either the key was checked, or it was handed to a tool that will check it.

\paragraph{The names, if you meet them.} The schema records this ownership on every
object, and the words surface in diagnostics and in the schema files, so they are worth
recognising: a surface \Jtwo\ owns is \emph{closed} (an unknown key is an error), one it
hands on is \emph{delegated} (unknown keys pass through unread), and a third kind,
\emph{open}, is a surface nobody owns yet --- it passes keys through but warns once,
saying so and why. Nothing in Part~\ref{part:task-card} requires you to remember these;
each chapter states plainly which of its keys are checked.

\section{How a card is loaded}
\label{sec:card-loading}

\cli{Jarvis run}, \cli{Jarvis check} and \cli{Jarvis validate} all put the card through
the same five layers, in this order. Knowing the order tells you which layer produced a
complaint, and therefore what kind of fix it wants:

\begin{enumerate}
  \item \textbf{Parse.} \code{yaml.safe\_load}; the top level must be a mapping.
        Failures here are syntax, not semantics --- a stray tab, an unclosed quote.
  \item \textbf{Character gate.} Keys and string values in your document must be
        \textsc{ascii}. This catches the classic disaster of a curly quote or a full-width
        colon pasted in from a chat window, which \textsc{yaml} accepts and no program
        can use.
  \item \textbf{Normalisation.} Historical spellings are folded to their modern
        equivalents, defaults are filled in, and the loader stamps in the resolved paths
        (project root, output root, scan name --- Section~\ref{sec:projects}).
  \item \textbf{Schema.} The card's structure and types, and which keys \Jtwo\ checks
        rather than passes on (Section~\ref{sec:zones}). This is where an unknown key, or
        a string where a number belongs, is caught.
  \item \textbf{Contracts.} Everything a schema cannot express: that \code{min} is below
        \code{max}, that a required key exists \emph{for the method you chose}, that a
        path resolves, that an operator can be imported.
\end{enumerate}

Layers 4 and 5 report into one combined report, so you never fix a schema error, re-run,
and only then discover a contract error underneath it.

\section{Reading a validation report}
\label{sec:validation}

\cli{Jarvis validate <card>.yaml} runs layers 1--5 and starts nothing
(Section~\ref{sec:cli-validate}). A card that passes says so in one line. A card that
fails prints the same report every time, in three parts:

\begin{terminal}
\begin{jcmd}
Jarvis validate bin/Example_Bridson.yaml
\end{jcmd}
\termsep
\begin{jout}
Config validation failed (2 error(s), 0 warning(s)):

Error summary (reference only):
+---+-------------+-----------------+------------------------+
| # | Code        | YAML path       | Problem                |
+---+-------------+-----------------+------------------------+
| 1 | JV2-SCH-001 | $               | Additional properties  |
| 2 | JV2-MTH-003 | Sampling.Method | 'Bridsonn' is not ...  |
+---+-------------+-----------------+------------------------+

Detailed diagnostics:
  [error] JV2-MTH-003  Sampling.Method
          'Bridsonn' is not implemented in Jarvis-HEP V2. Available: AM,
          AMMCMC, AdaptiveBridson, Bridson, CSV, DEMCMC, DRAM, Dynesty, ...
          suggestion: Choose an implemented Method, then provide its
          required Bounds configuration.
          example:
            Sampling:
              Method: Random
              Bounds:
                Point number: 100
                Seed: 0
              Variables:
                - name: x
                  distribution:
                    type: Flat
                    parameters: {min: 0.0, max: 1.0}
\end{jout}
\end{terminal}

The three parts do different jobs, and the third is the one to read:

\begin{keylist}
  \item[the count line] How many errors and how many warnings. Warnings do not stop the
        run unless you passed \cli{--strict}.
  \item[the summary table] One line per problem, for scanning. It is labelled
        \emph{reference only} because a truncated message is not enough to fix anything.
  \item[the detailed diagnostics] The real content: the \textbf{code}, the exact
        \textsc{yaml} \textbf{path}, the message, and --- where the validator knows the
        answer --- a \code{suggestion} in words and an \code{example} of correct
        \textsc{yaml} you can paste.
\end{keylist}

That last point is the part worth internalising. For a large class of mistakes you do not
have to come back to this book at all: the validator names the key, tells you what to do,
and prints the fix.

\subsection{The code tells you which chapter to open}
\label{sec:code-families}

Every finding carries a stable code of the form \code{JV2-<family>-<number>}. The codes
themselves are contract-stable, so they are safe to grep for in \textsc{ci} logs --- but
their more useful property is that \textbf{the family names the part of the card that is
unhappy}, and therefore the chapter that explains it (Table~\ref{tab:code-families}):

\begin{table}[ht]
  \footnotesize
  \begingroup
  \setlength{\tabcolsep}{0pt}
  \begin{tabular}{@{}p{0.255\linewidth}p{0.213\linewidth}p{0.532\linewidth}@{}}
    \toprule
    \textbf{Family} & \textbf{Where} & \textbf{Go to} \\
    \midrule
    \code{JV2-YAML-*} & the file itself & the parse failed; fix the \textsc{yaml} syntax \\
    \code{JV2-ENC-*}  & the file itself & a non-\textsc{ascii} key or string value \\
    \code{JV2-SCH-*}  & any block & unknown key or wrong type (\S\ref{sec:zones}) \\
    \code{JV2-LOAD-*} & the file itself & the card could not be loaded at all \\
    \code{JV2-ENV-*}  & \yamlkey{EnvReqs} & Chapter~\ref{ch:envreqs} \\

      Chapter~\ref{ch:dynesty} \\
    \code{JV2-MOD-*}  & \yamlkey{Calculators.\allowbreak{}Modules} & Chapter~\ref{ch:calculators} \\

    \code{JV2-OPR-*}  & \yamlkey{Operas} & Chapter~\ref{ch:operas} \\
    \code{JV2-DEAD-*} & anywhere & warning: the key is accepted and then ignored \\
    \bottomrule
  \end{tabular}
  \endgroup
  \caption[Code families and the chapter that explains them.]{Code families and the
  chapter that explains them. The family in a failing code is the fastest index into
  Part~\ref{part:task-card} this book has.}
  \label{tab:code-families}

Two families are worth recognising on sight. \code{JV2-SCH-001} is \emph{unknown key} ---
its suggestion lists every legal key at that level, so it is nearly always a typo you can
fix without leaving the terminal. \code{JV2-DEAD-*} is the opposite shape: the key is
spelled correctly, is accepted, and does nothing. Run with \cli{--strict} and it becomes
an error, which is how you find settings you believe are taking effect and are not.

\section{\yamlkey{Scan}: naming the run}
\label{sec:scan-block}

\yamlkey{Scan} is the one top-level block that fits in this chapter, because the runtime
reads exactly two keys from it.

\begin{yamlwin}
Scan:
  name: EggBox_Dynesty          # the scan's identity, everywhere
  sample_directory:             # optional; full reference in Chapter 6
    limit: 200
    archive_samples: true
\end{yamlwin}

\begin{keylist}
  \item[name] The scan's identity, and the only key most cards set. It becomes the output
        directory \file{outputs/<name>/}, the log directory \file{logs/<name>/}, the
        checkpoint directory, the \code{<scan>} half of every process title
        (\S\ref{sec:cli-run}), and the name the runtime-control commands list
        (\S\ref{sec:cli-ps-kill}). Defaults to \code{default}, which is a poor name for
        anything you intend to keep.
  \item[sample\_directory] The \file{SAMPLE/} bucket policy --- how many Samples per
        bucket, how they are packed and pruned. The same map is also accepted under
        \yamlkey{EnvReqs.V2}; when both are present \textbf{the one here wins}. Every key
        is documented once, in Section~\ref{sec:sample-directory}.
\end{keylist}

Because \yamlkey{Scan.name} is what isolates one run from another, two scans may not
share it while both are alive --- the second is refused at startup rather than allowed to
write into the first one's directories (\S\ref{sec:cli-run}).

\begin{jwarn}
\yamlkey{Scan.save\_dir} is accepted by the schema and then ignored: the output root is
always \file{<project-root>/outputs/<scan-name>}. A card that sets it validates cleanly
and writes its results somewhere else than you asked. If you need outputs elsewhere, move
or link the project directory (Section~\ref{sec:projects}).
\end{jwarn}
